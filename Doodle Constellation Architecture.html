Doodle Constellation Architecture

Doodle Constellation

From the architecture wiki

This article is about the architecture of sketch-to-sky matching systems, using the Doodle Constellation design as its reference. For related systems that identify photographs of the sky, see Variants. The reference build is a desktop program in OCaml with raylib-ocaml. Each component below ends with how it is built there, and the algorithm lineage shows which parts are adapted from GIMP.

A Doodle Constellation system takes a shape a person draws on a phone or in a desktop window and finds a set of real stars whose arrangement on the sky matches it. The result behaves like a personal asterism, an informal star pattern as opposed to one of the 88 official IAU constellations. The system then shows where that patch of sky is, when it is best placed for the user tonight, and tells a short invented myth about it.

The input is a single stroke, simplified to a handful of corner points. The output is a list of named stars, the rotation and scale that map the drawing onto them, a fit-quality number, and a rendered sky view. The defining property is similarity invariance: a drawing matches a star pattern no matter how large it was drawn or which way it was turned.

The core problem is a form of point-set registration without known correspondences. The system solves it the way astronomical plate solvers do, by hashing small groups of stars into shape keys that ignore position, scale and rotation, so that a drawing can be looked up instead of compared against every possible star combination.

Overview

The system is usually split into two tiers. The offline tier runs once, when the service starts: it loads a catalogue of bright stars and precomputes an index of the shapes that small groups of nearby stars make. The online tier runs for every drawing: it simplifies the stroke, looks up candidate star groups in the index, fits and scores each candidate, and hands the winner to the presentation layer.

The presentation layer has three parts that run side by side once a match exists. A renderer draws the sky and animates the drawing onto it, a visibility calculator works out when the region is highest from the user's location, and a narration layer turns the star names into a spoken story. Only the online matching path is time-critical; everything after it can stream in.

Architecture

Sketch capture

The sketch capture component is the drawing surface. It records the user's finger or mouse path as an ordered list of screen points, plus an optional name for the shape. It hands the raw stroke to the stroke simplifier. It owns no lasting state beyond the current drawing, and it exists so that every later stage receives clean, ordered geometry rather than input events.

Stroke simplifier

The stroke simplifier reduces hundreds of jittery points to the 5 to 9 corners that carry the shape, typically with the Ramer–Douglas–Peucker algorithm, which drops points that lie close to the line between their neighbours. It receives the raw stroke from sketch capture and passes the corner list to the candidate generator, rejecting shapes that are too simple (a straight line) or too complex. A star pattern has only a few stars, so matching the raw stroke would compare unlike things.

In the OCaml + raylib build

ModuleSimplify
raylib callsnone (pure OCaml)
Adapted fromgimpboundary.c simplify_subdivide: recursive subdivision with a cross-product distance test and a special case for closed loops.
What changesGIMP splits each piece at its midpoint. Doodle splits at the farthest point, which is true Ramer–Douglas–Peucker. The tolerance is relative to the drawing's size, and a retry loop lands the result on 5 to 9 corners. Smoothing moves into Capture, so the stroke arrives already smoothed.
  1. Set ε to 4% of the stroke's bounding-box diagonal.
  2. Line check: if no point is farther than 8% of the diagonal from the first-to-last chord, return Error `Too_simple.
  3. RDP on the range [i, j]: for each point p between them, d = |dx·(a.y − p.y) − dy·(a.x − p.x)|, with a = point i and (dx, dy) = point j − point i. This is GIMP's test: it equals the true distance times the chord length, so compare it with ε·length and skip the square root inside the loop.
  4. If the largest d is at most ε·length, keep only point i. Otherwise recurse on [i, k] and [k, j], where k is the farthest point.
  5. Closed stroke (start within ε of end): measure plain distance from the start point instead, as GIMP does when both ends coincide.
  6. Count the corners. Over 9: raise ε by 30%. Under 5: lower it by 30%. Try at most 5 times, then return Error `Too_complex or `Too_simple.
type reason = [ `Too_simple | `Too_complex ]
val corners : Geom.pt array -> (Geom.pt array, reason) result

Star catalogue store

The catalogue store holds every star the system may use, with its position in the equatorial coordinate system (right ascension and declination), its apparent magnitude (brightness, where smaller numbers are brighter), a proper name where one exists, and its parent constellation. It is filled from a public source such as the Bright Star Catalogue or a subset of the Hipparcos catalogue, cut to stars bright enough to see without a telescope. It supplies positions to the index builder and to the fitter.

Invariant index builder

The index builder takes every small group of nearby stars, usually triangles within about 25 degrees of each other, and describes each by numbers that stay the same under moving, scaling and rotating: the ratios of its side lengths and one of its angles. It projects each local patch of sky onto a flat plane first, using a gnomonic projection, so that flat-geometry measurements are valid. These shape keys are rounded into bins and stored in a hash table that maps each key to the star groups that produce it. This is the technique called geometric hashing. The index is what turns an otherwise enormous search into a lookup.

Candidate generator

The candidate generator receives the simplified drawing, forms triangles from its corners, computes the same shape keys, and looks each up in the index, tolerating one bin of error to allow for a shaky hand. Every hit is a hypothesis: these three drawn corners might be those three stars. From each hit it derives the similarity transform (a scale, rotation and shift) that would place the drawing on the sky, and passes these hypotheses to the fitter. It owns nothing persistent.

ModuleCandidates (uses Geom.sim_of_pair)
raylib callsnone (pure OCaml)
Adapted fromThe two-handle case of the Handle Transform tool, gimptoolhandlegrid.c case 2, and gimptoolpolygon.c fit_segment: one pair of points fixes scale, rotation and shift. Commit 2989bad35a.
What changesGIMP moves image handles. Doodle returns the transform as a record, and chooses the triangle's longest side as the pair because a long baseline gives the steadiest angle.
  1. Form every triangle of 3 corners (at most 84 for 9 corners).
  2. Key: sort the sides by length, take the two ratios short/long and middle/long and the angle opposite the longest side, and round each to a bin. Sorting fixes which corner matches which star.
  3. Look up the key and its 26 neighbouring bins (±1 in each of the 3 parts) with Hashtbl.find_all.
  4. For each hit, pair the drawn longest side (a, b) with the star longest side (A, B).
  5. Similarity: s = |B − A| / |b − a|; θ = atan2(B − A) − atan2(b − a); shift t = A − s·R(θ)·a. Then T(p) = s·R(θ)·p + t.
  6. Emit the hypothesis. Nothing is stored between drawings.

Similarity fitter and scorer

The fitter tests each hypothesis against the whole drawing. It projects every remaining corner onto the sky, finds the nearest unused bright star to each by nearest neighbour search, and refines the transform with Procrustes analysis, the least-squares way of overlaying one point set on another. It scores the result by the root-mean-square deviation between corners and stars, penalised for faint stars and for bright stars that fall inside the shape but were not used. Trying many hypotheses and keeping the one most of the points agree with follows the logic of RANSAC. The best match goes to the renderer, the visibility calculator and the narration layer.

In the OCaml + raylib build

ModuleFitter (uses Geom.procrustes)
raylib callsnone (pure OCaml)
Adapted fromSnap-to-nearest with a running minimum inside a radius, from gimpimage-snap.c snap_point. The epsilon pivot guard in gimp-transform-utils.c mod_gauss and commit e7b6103cc8. The sign-flip fix in 17ec3d130e is the model for the mirror pass.
What changesGIMP only solves exact transforms from 4 point pairs. Least-squares Procrustes over all corners is new code. So are the rule that each star is used once and the score penalties.
  1. Apply the hypothesis transform to every corner on the tangent plane.
  2. Snap: for each corner, scan the stars in the patch and keep the nearest unused one within radius r, tracking a running minimum distance.
  3. Centre both point sets on their centroids c_p and c_q. If Σ|p′|² is below 1e-9, drop the hypothesis (compare with an epsilon, never with exact zero).
  4. Procrustes: a = Σ(p′ₓq′ₓ + p′ᵧq′ᵧ), b = Σ(p′ₓq′ᵧ − p′ᵧq′ₓ). Then θ = atan2(b, a), s = √(a² + b²) / Σ|p′|², t = c_q − s·R(θ)·c_p.
  5. Repeat snap and refit twice, because a better transform can change which star is nearest.
  6. Score: RMS error in degrees, plus a penalty for faint stars and for bright stars inside the shape that were not used. Keep the best. If mirror images are allowed, run again with y → −y and keep the better result.
  7. Set weak = rms_deg > accept_limit. This makes the fitter the owner of the weak-match rule.

Sky renderer and morph animator

The renderer draws the region of sky around the match, usually with a stereographic projection, which preserves the shapes of small patterns and is the traditional projection of star charts. It then animates the user's drawing sliding, turning and scaling onto the matched stars, a simple form of morphing, and labels each star. It also assembles the shareable sky card. It receives the match from the fitter, the viewing time from the visibility calculator and the audio from the narration layer.

Visibility calculator

The visibility calculator converts the matched region's centre into the horizontal coordinate system (altitude above the horizon and compass direction) for the user's location and date. It finds the region's culmination, the moment it crosses the meridian and stands highest, and checks whether that happens in darkness. Star positions barely change, so no full ephemeris is needed unless planets or the Moon are shown. It hands the best viewing time and direction to the renderer.

Narration layer

The narration layer receives the shape's name, the matched star names and the neighbouring official constellation. A language model writes a short myth from only those facts, and a speech synthesis service reads it aloud. The story is labelled as fiction, and no astronomical number is allowed into it except those passed in. It exists for engagement; the matching works without it.

Architecture diagram

Operation

Matching a drawing

A user draws a lightning bolt. Sketch capture records about 200 points; the simplifier reduces them to six corners. The candidate generator forms the triangles among those corners and looks up each one's shape key, collecting a few thousand hypotheses. The fitter projects all six corners for each hypothesis, snaps them to the nearest bright stars and keeps the tightest fit, for example six stars near Orion with an error under two degrees. The renderer morphs the bolt onto those stars while the visibility calculator reports that the region is highest at about 2:40 a.m., and the narration layer begins its story.

Sanity check with a known pattern

Drawing the seven stars of the Big Dipper should return the Big Dipper as the top match with a very small error. Because the real pattern is in the catalogue, this test checks the whole online path at once and is the usual first test of a new build.

Failure: a shape with no good match

A drawing with long, evenly spaced corners may find no star group that fits well, because bright stars are not spread evenly over the sky. The fitter still returns its best hypothesis, but its error exceeds the acceptance threshold. The system then reports the fit as weak, shows the best attempt dimmed, and suggests fewer corners or a tighter shape. A second failure occurs when a shape is too simple, such as three nearly collinear corners: the simplifier rejects it before any lookup, because a line matches countless star groups equally well.

Properties

  • Similarity invariance. A match does not depend on where, how large, or at what angle the shape was drawn. The invariant index builder and candidate generator provide it, through shape keys built from ratios and angles; see similarity.
  • Interactive speed. Results arrive in a few seconds because the index replaces exhaustive comparison with lookups in a hash table, which take roughly constant time per key.
  • Robustness to a shaky hand. Bin tolerance in the candidate generator and least-squares refinement in the fitter absorb small drawing errors. Outlier corners are handled by the hypothesis-and-verify approach of RANSAC.
  • Findability. Every matched star is bright enough to see without optical aid, enforced by the catalogue cut and the fitter's magnitude penalty, so the result can be found on a real night.
  • Measurable fit quality. The fitter reports a root-mean-square deviation in degrees, so users can see how close the match is instead of trusting a pleasing picture.
  • Honest separation of fact and fiction. Star positions, names and times come from data; only the myth is generated, and it is labelled as such.

Design trade-offs

Catalogue depth. Including fainter stars makes almost any shape matchable but produces matches no one can see from a city. Cutting at about magnitude 4 to 5 keeps matches findable at the cost of rejecting more drawings.

Shape key size. Triangles are cheap to index and match from any three corners, but they are not very distinctive, so they return many false hypotheses. Four-star groups, the "quads" used by Astrometry.net, are far more distinctive but make the index much larger and need four well-placed corners.

Bin width. Wide bins tolerate sloppy drawing but flood the fitter with candidates; narrow bins are fast but miss imperfect drawings. A common compromise is narrow bins with a one-bin neighbourhood search.

Scoring. Pure RMS error favours tiny, tight patterns of faint stars. Adding brightness and "unused bright star inside the shape" penalties makes results look right to a person, at the cost of extra tuning.

Projection. Matching on a gnomonic tangent plane keeps the geometry exact for small regions but distorts large ones; displaying with a stereographic view keeps shapes recognisable. Using different projections for matching and display is normal.

Where matching runs. Running on a server keeps the index off the phone and allows heavier scoring. Running in the browser removes network delay and works offline, but the index must be small enough to download. The OCaml build takes neither route: everything runs in one desktop process, the raylib loop calls the matcher as an ordinary function, and the index is built in memory at startup.

Algorithm lineage

Five of the nine components reuse techniques found in the source of GIMP, the open-source image editor. GIMP solves related problems: it cleans up pen input, reduces outlines to fewer points, and moves shapes so that chosen points land on chosen targets. Three points matter for the OCaml build. First, GIMP's simplifier is not exact Ramer–Douglas–Peucker: it splits at the midpoint, so only its distance test and recursion are reused. Second, GIMP has no least-squares fit, so Geom.procrustes is written from the standard closed form. Third, GIMP's application code is licensed under the GPL version 3, so the OCaml modules reimplement the techniques instead of translating the C code line by line.

All matching modules work on a plain record, {x; y}, and never on raylib's Vector2.t. Only main.ml and Sky call raylib. This keeps the algorithms testable with dune test without opening a window.

Variants

Photograph plate solving. Systems such as Astrometry.net take a photograph instead of a drawing, detect the stars in it, and identify exactly which part of the sky it shows. The architecture is the same, but the input points come from star detection, and the catalogue is much deeper.

Spacecraft star identification. A spacecraft star tracker photographs the sky and matches star patterns against an onboard catalogue to work out which way the spacecraft is pointing. It is the same lookup problem under tight memory and time limits.

General point-set registration. Without the sky, the same pipeline aligns any two point clouds, as in point-set registration, which is used in robotics, medical imaging and 3D scanning.

Constellation teaching tools. Planetarium software draws the traditional constellations and asterisms. A Doodle Constellation system reverses that relationship by letting the user supply the pattern.

History

The 88 modern constellations were adopted by the International Astronomical Union in 1922, with fixed boundaries following in 1928. Geometric hashing came from computer vision research on object recognition in the late 1980s, and was later reused in other fields. Its best-known astronomical use, blind identification of sky photographs, was described in the Astrometry.net paper published in The Astronomical Journal in 2010. Doodle Constellation applies the same index-and-verify design to freehand drawings, playing on the human tendency, known as pareidolia, to see familiar shapes in random patterns.

Building one

Minimal version (about two hours), in OCaml and raylib. One dune project with a pure library and a small raylib executable. Pre-built: Capture, Catalogue, Index, Candidates and the flat Sky plot. The small core to write by hand is the three adapted algorithms, Simplify.corners, Geom.sim_of_pair and Geom.procrustes, plus Fitter.best that ties them together. It can match 5 to 7 corner drawings and pass the Big Dipper test. It cannot show viewing times, animate, narrate, or handle shapes that need faint stars.

Hackathon version (a day). Adds Morph and the stereographic Sky renderer with the morph animation, the visibility calculator for the user's location, the narration layer, fit-quality display, and the share card saved with take_screenshot. Narration runs in its own Domain so the frame loop never waits on the network.

Product version. Adds four-star keys for better precision, an in-browser index for offline use, saved constellations, multiplayer "draw one for a friend", and pointing hardware or a telescope mount that aims at the result.

Questions to answer before building

  • What brightness cut makes matches findable from a typical city sky?
  • Triangles or four-star groups, and how far apart may stars in one group be?
  • How wide is a bin, and how many neighbouring bins does a lookup check?
  • What score separates a good match from a weak one, and what does the user see for each?
  • Does the drawing's direction matter, and are mirror images allowed?
  • How long may the index take to build at startup before the window feels slow, and should building move to a separate Domain?
  • Which projection is used for matching, and which for display?
  • Which facts may the story mention, and how is it marked as fiction?
